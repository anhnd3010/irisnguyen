Melon Website Design Project

About the project

Melon is a facial recognition API platform for developers and enterprises, with flexible deployment options across Cloud, On-premise and Edge devices.

The project redesigned Melon's product website together with its developer portal, turning a powerful but fairly complex technology into an experience that is easy to understand and easy to start with. Developers needed to grasp the product's value within moments, get an API key quickly and begin integrating, while IT teams and enterprise decision-makers needed to explore the architecture, deployment models and relevant use cases on their own, without depending on a sales consultation. The new site was positioned as a bridge between product marketing and technical documentation, guiding users seamlessly from discovering the product → choosing a deployment option → reading the API docs → getting an API key → starting the integration.

Melon is already trusted by Japanese enterprises including Keisei Electric Railway, Marubeni, Marubeni I-DIGIO, Sanwa Systems and Matsumura, so the new experience also had to balance enterprise-grade credibility with developer self-service.

Problem Statement

Two audiences, one website, and neither could find what they needed

Developers want to try it right away. Enterprises want to know where face data is stored. When those two journeys get tangled together, both audiences leave. The Discover phase surfaced three key friction points.

  1. Awareness

    Unclear what Melon offers

    The four deployment models were described in internal jargon, so newcomers struggled to tell the API, Local Server and Hardware Terminal apart.

  2. Activation

    The path to an API key was too long

    Technical docs lived apart from the marketing site, with no Quick Start or sample code, leaving developers to guess the next step.

  3. Conversion

    Enterprises lacked trust signals

    Biometric data is sensitive. Without transparent pricing, clear privacy information and an on-premise option, IT teams won't leave their contact details.

User goals

  • Understand the product and choose the right deployment model
  • Try the API for free, with sample code that runs out of the box
  • Read the docs comfortably on desktop and mobile, even late at night
  • Know the cost before having to talk to sales

Business goals

  • Grow self-serve developer sign-ups on the free plan
  • Increase qualified enterprise leads through Contact Sales

  • Lay the groundwork for the Melon Ecosystem

How might we help developers go from “hearing about Melon” to “a successful API call” in a single visit, while giving enterprises enough confidence to leave their contact details?

Research

Listening to both audiences before designing for either

Four research methods covered the business, its users and the market, so that every design decision could be traced back to what developers and enterprise buyers actually said.

  • Stakeholder interviews

    PM, CTO, the Japanese sales team and customer success, to clarify business goals and technical constraints.

  • User interviews

    Backend and mobile developers, plus IT managers who had integrated eKYC or access-control systems.

  • Competitor groups

    Analysed the websites, pricing, docs and onboarding of each group of face API providers.

  • Heuristic review

    Scored industry developer docs against Nielsen's 10 usability heuristics.

Key insights & How Might We

Insight 1

Developers judge a product by its code, not its copy

They skim past the marketing and look straight for a code sample or a “try for free” button. If neither is on the first screen, they leave.

HMW put code and a “Start Building Free” CTA right in the hero, then lead straight into Quick Start?

Insight 2

For enterprises, privacy is a prerequisite

The first question is always where face data is stored. On-premise isn't a side feature; it's the reason to buy.

HMW present Local Server as an equal alternative to Cloud, on the same API?

Insight 3

Docs are read in many different contexts

On an ultrawide monitor while coding, on a phone during a meeting, and late at night during an incident. One fixed layout can't serve all three.

HMW design docs that adapt to any screen, with dark mode, search and Quick Access on mobile?

Insight 4

Buyers need material to convince others

IT managers rarely decide alone. They need plan comparisons, FAQs and clear information to take to leadership.

HMW turn the Pricing page into a decision-making tool, with plans, a comparison table, an FAQ and a contact CTA?

Storyboard

One afternoon, from a new request to a successful API call

The storyboard follows Kenta's ideal experience with the new design. Each frame maps to a specific screen in Figma, so the whole team could share the same story before any wireframes were drawn.

  1. 1 · Context

    A new request

    His PM assigns a face verification feature, due in two sprints. Kenta searches for “face recognition API”.

  2. 2 · Homepage

    Clear in 10 seconds

    The hero states “Facial Recognition API for Modern Applications”, right next to a Start Building Free button.

  3. 3 · Built for Developers

    Real code, up front

    Sample code and SDKs for Python, JavaScript and Java convince him to click “Learn more”.

  4. 4 · Developer Hub

    Step 1: get an API key

    The Developer Hub breaks onboarding into clear steps. Kenta has a key within minutes.

  5. 5 · Docs dark mode

    Coding at 11pm

    Docs in dark mode, a copy button on every code block, and a table of contents that follows his place on the page.

  6. 6 · Outcome

    The first request succeeds

    He sends the Pricing link to his boss to compare plans, and the journey hands over to Yuki.

Sitemap

Separating “the product”
from “for developers”

Card sorting with developers and the sales team showed that people navigate by deployment model, not by feature name. The main navigation was therefore cut to four items (Products, Developers, Pricing and Contact), with a Contact Sales button always visible in the top-right corner.
